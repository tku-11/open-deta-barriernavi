# P6 サーバー側ページングとお気に入り優先順

**決定日:** 2026-08-21
**目的:** スコア一覧のAPIが返すページ単位の`data`と全件数`total_count`を、一覧画面がそのまま利用する。100件を超える結果でも、お気に入り駅を全検索結果の先頭に優先表示する。

## 1. 解消する不整合

従来の一覧画面は`limit=10000`で全件を取得しようとし、クライアント側でお気に入り優先・ページングを行っていた。しかし、スコアAPIの`limit`は100を上限とするため、`total_count`が100を超えると後半ページが空になる可能性があった。

P6では、一覧画面が`limit=10`と`offset=(page-1)*10`をAPIへ送る。画面に描画するデータはAPIから返った当該ページの`data`だけとし、総ページ数は`total_count`だけで計算する。

## 2. お気に入り優先順

スコア一覧APIは、任意の`favorite_station_ids`クエリパラメータを受け付ける。値はJSON配列とし、正の整数だけを重複なく最大100件まで採用する。不正JSON、配列以外、文字列、真偽値、0以下の値は無視する。

処理順序は以下のとおりである。

1. 既存の検索、都道府県、路線、設備フィルタを適用する。
2. 既存のスコアソートまたは駅名順を適用する。
3. フィルタ後の全結果から、お気に入りに該当する駅を既存順のまま先頭へ安定移動する。
4. その順序に対して`offset`と`limit`を適用する。

> `favorite_station_ids`を指定しない既存リクエストでは、P5以前と同じ順序、`data`、`count`、`total_count`を返す。

## 3. 責務境界

| 層 | 実装 | 責務 |
| --- | --- | --- |
| スコア駅Blueprint | `backend/routes/scored_stations.py` | 任意パラメータを安全に検証し、ページング前の安定したお気に入り優先順を確定する。 |
| 一覧画面 | `frontend/src/index.ts` | 現在ページから`limit`・`offset`を構築し、プロフィールから取得したお気に入りIDを任意パラメータとして送る。APIのページデータをそのまま描画する。 |
| スコアAPI | 既存URLとレスポンス | `data`、`count`、`total_count`、既存の`limit`上限100と`offset`正規化を維持する。 |

## 4. 回帰防止

`test_station_api_contract.py`に、お気に入り優先順がページング前に適用されること、未指定時の順序互換、不正な`favorite_station_ids`の無害化を追加した。P6完了時点で、Python構文検証、32件の自動テスト、TypeScriptビルドを成功させた。

実行中アプリでは、通常順で59番・87番だった駅について、87番をお気に入り指定すると先頭ページが87番、次ページが59番になり、`total_count`が130のまま維持されることを確認した。
