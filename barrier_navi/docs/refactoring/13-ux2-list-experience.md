# UX-2: 駅一覧の検索・比較体験

## 目的

UX-2では、駅の一覧検索で「何件が、どの条件で、どの順序で表示されているか」を視覚とテキストの両方で把握できるようにした。既存の駅API、スコア定義、サーバー側ページング、お気に入り優先順は変更していない。

| 対象 | 改善内容 | 保持した契約 |
| --- | --- | --- |
| 検索結果 | 表示件数範囲、総件数、現在の並び順を要約する | `limit`、`offset`、`total_count` |
| 絞り込み | 条件数、AND条件、プロフィール由来条件を明示する | `filters` のJSON形式 |
| お気に入り | 優先表示されている駅数とカード上の状態をテキストでも示す | `favorite_station_ids` の優先順 |
| 空状態 | 条件を緩める案内と条件リセット操作を示す | 検索・フィルタ状態 |
| モバイル | 結果を先に表示し、絞り込みを明示的に開閉する | デスクトップの2カラム表示 |

## 実装判断

### 検索結果の要約

各一覧ページに `result-summary` を追加した。読み上げ用の状態通知とは分離し、表示対象、範囲、並び順、適用中の条件数を常に確認できる領域とした。これにより、ライブリージョンが同じ情報を繰り返し通知することを避けながら、検索結果の文脈を画面上に残している。

お気に入り駅が登録されている場合は「お気に入り N駅を優先表示」と表示する。これは星や枠線だけに依存せず、サーバー側で既に実施している優先順を利用者に説明するための補助表示である。

### プロフィール由来の設備条件

ログイン済みの利用者に優先設備を適用した場合、適用中の設備条件には「プロフィールから適用」と明記する。さらに、現在の検索だけからその条件を外す操作とプロフィール画面へのリンクを提示する。

> 「この検索から外す」は、保存済みのプロフィールを変更しない。一覧画面のチェック状態だけを更新し、次回のプロフィール自動適用時には保存済みの優先設備を引き続き利用する。

検索リクエスト直前に設備チェックボックスの状態から `selectedFilters` を再構成するよう整理した。これにより、チップやプロフィール由来条件を外した操作が、以前の状態とマージされて復活することを防ぐ。

### 比較と空状態

駅カードには達成項目数と達成率をテキストで併記した。お気に入りおよび優先条件一致もバッジの文字で伝え、色だけに依存しない。

該当駅が0件の場合は、設備条件・地域・検索語の見直しを案内し、同じ場所から「条件をリセットして再検索」を実行できる。利用者が戻る場所を探さずに再試行できるようにするためである。

### モバイルの絞り込み

幅960px以下では駅一覧を先に表示し、絞り込みパネルは初期状態で閉じる。開閉ボタンは `aria-controls` と `aria-expanded` を持ち、キーボードでも操作できる。デスクトップでは従来どおり一覧と絞り込みを2カラムで常時表示する。

## 回帰条件

| 項目 | 確認内容 |
| --- | --- |
| 静的マークアップ | 身体・聴覚・視覚の全一覧に結果要約、フィルタ開閉ボタン、関連付けられたフィルタ領域がある |
| 条件解除 | プロフィール由来条件を一覧上から外しても、保存済みプロフィールは変更しない |
| 表示順 | お気に入り優先は既存のサーバー側処理をそのまま利用する |
| アクセシビリティ | 開閉状態が `aria-expanded` へ反映され、要約・バッジ・達成項目数はテキストでも読める |
| ビルド成果物 | `frontend/src/index.ts` の変更を `frontend/dist/index.js` に同期する |

## 検証

Python構文検証、バックエンドの全ユニットテスト、フロントエンド単体テスト、TypeScriptビルド、ローカルHTTP応答を確認する。UX-2の静的回帰は `backend/tests/test_accessibility_markup.py` に追加する。
